# Q002. Разница между Redux и Flux?

> **Источник:** [17. state-management.md](../17.%20state-management.md) · **Тема:** State Management

---

## Короткий ответ

**Flux** — архитектурный паттерн от Facebook для управления однонаправленным потоком данных, а **Redux** — конкретная библиотека, вдохновлённая Flux и Elm. Ключевые отличия: в Flux может быть несколько Store и Dispatcher, в Redux — один Store и нет Dispatcher (его роль выполняет `store.dispatch`). Redux добавляет строгую иммутабельность, редьюсеры как чистые функции и поддержку middleware.

---

## Развёрнутый ответ

### Суть и определение

**Flux** (2014, Facebook) — паттерн, а не библиотека. Описывает однонаправленный поток: `Action → Dispatcher → Store → View`. Реализаций Flux было множество (Alt, Reflux, McFly), но все они следовали одному принципу.

**Redux** (2015, Дэн Абрамов) — конкретная библиотека, синтезировавшая идеи Flux (однонаправленный поток) и Elm (иммутабельное состояние, чистые функции). Redux упростил Flux, убрав Dispatcher и объединив все Store в один.

### Как это работает

**Flux flow:**
```
Action Creator → Dispatcher → Store (может быть несколько) → View
                     ↑
              (Dispatcher регистрирует
               обработчики каждого Store)
```

**Redux flow:**
```
Action Creator → store.dispatch(action) → Reducer (чистая функция) → Store (один) → View
```

Dispatcher в Flux — синглтон, который рассылает каждый action во все зарегистрированные Store. Каждый Store сам решает, реагировать ли на данный action. В Redux эту роль выполняет сам `dispatch` + `combineReducers`: каждый под-редьюсер обрабатывает свою часть состояния.

### Практика и применение

Flux как паттерн сейчас исторически важен, но почти не используется напрямую — его вытеснил Redux (и другие библиотеки). Понимание Flux помогает понять, почему Redux сделан именно так:

- Множественные Store в Flux создавали проблему зависимостей между ними (`waitFor`); Redux решил это единым деревом состояния
- Отсутствие чистых функций в Flux делало time-travel debugging невозможным; Redux это исправил
- В Flux логика в Store была смешана с подпиской на изменения; Redux разделил эти обязанности

### Важные нюансы и краеугольные камни

- В Flux Store могут содержать **мутабельное** состояние и бизнес-логику — нет ограничения на чистоту
- Flux `waitFor` позволял одному Store ждать обновления другого — в Redux это решается через структуру редьюсеров
- Redux **строже**: редьюсеры обязаны быть чистыми, что даёт детерминизм, но требует иммутабельных операций
- Оба используют **однонаправленный поток** — это общее и главное сходство

### Примеры

```javascript
// Flux — Store самостоятельно управляет состоянием (концептуально)
class UserStore extends EventEmitter {
  constructor() {
    super();
    this._user = null;
    AppDispatcher.register((action) => {
      if (action.type === 'SET_USER') {
        this._user = action.payload;   // мутация разрешена
        this.emit('change');
      }
    });
  }
  getUser() { return this._user; }
}

// Redux — редьюсер как чистая функция (нет мутаций, нет подписки внутри)
function userReducer(state = null, action) {
  switch (action.type) {
    case 'SET_USER': return action.payload;   // новый объект, не мутация
    default:         return state;
  }
}
```

## Сравнение

| Критерий | Flux | Redux |
|----------|------|-------|
| Тип | Паттерн/архитектура | Конкретная библиотека |
| Количество Store | Много (по одному на домен) | Один глобальный Store |
| Dispatcher | Явный синглтон | Отсутствует (встроен в `store.dispatch`) |
| Мутабельность | Разрешена в Store | Запрещена; редьюсеры — чистые функции |
| Middleware | Нет стандарта | Официальная поддержка (`applyMiddleware`) |
| Time-travel debugging | Невозможен (мутабельность) | Возможен (Redux DevTools) |
| Зависимости между Store | `waitFor` | Нет (единое дерево состояния) |
| Популярность сегодня | Устарел | Широко используется (+ RTK) |

## На что обратить внимание на собеседовании

### Каверзные follow-up (что спросят дальше)

- **Что такое Dispatcher в Flux?** — Централизованный реестр, рассылающий каждый action во все зарегистрированные Store; в Redux заменён встроенным `dispatch`.
- **Зачем Redux отказался от нескольких Store?** — Единый Store упрощает сериализацию, SSR, отладку и устраняет проблему зависимостей `waitFor`.
- **Почему в Redux нет Dispatcher?** — `store.dispatch` + `combineReducers` выполняют ту же функцию без явного синглтона.
- **Что общего у Flux и Redux?** — Однонаправленный поток данных: UI → Action → обновление состояния → UI.
- **Чем Redux отличается от Elm?** — Elm — полноценный язык с типами и архитектурой; Redux заимствовал концепцию `(model, msg) → model`, но оставил JS-свободу.

### Красные флаги (чего не говорить)

- «Flux и Redux — одно и то же» — Flux это паттерн, Redux это библиотека с конкретными правилами.
- «В Redux много Dispatcher'ов» — Dispatcher один (встроен), а Store всегда один.
- «Flux устарел, никто его не использовал» — Facebook использовал Flux в продакшене; Redux появился позже и улучшил подход.
